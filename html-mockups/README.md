# RoadReport HTML mockups

Standalone, static snapshots of every screen in the admin portal. They are meant
to be handed to a design AI (or a designer) with no repo access: open the HTML,
edit it, hand it back.

**Start with [`_system/index.html`](_system/index.html), then do one screen at a
time.** Do not redesign every screen independently — the shell, buttons, forms,
badges, tables and spacing must stay consistent.

---

## Open the mockups

From the repository root:

```bash
npm run mock:serve
# then open http://localhost:8080
```

Or open `html-mockups/index.html` directly in a browser. Every screen links its
CSS with relative paths, so the folder can be zipped and moved as one unit.

---

## What to edit

For each screen folder `_screens/<screen>/`:

| File | Edit? | Purpose |
|---|---|---|
| `index.html` | **Yes** | The screen markup. Keep the structure and annotations. |
| `screen.css` | **Yes** | Screen-specific styles. This is the main deliverable. |
| `notes.md` | **Yes** | Bullet list of what changed and anything the integrator must know. |
| `preview-desktop.png` | No | Reference screenshot. Regenerated by the exporter. |
| `preview-mobile.png` | No | Reference screenshot at 390 px. |
| `assets/` | No | Captured chart/map images. |

Everything in `_shared/` is **read-only**:

| File | Purpose |
|---|---|
| `_shared/app.css` | Copy of the real admin stylesheet. Design tokens and shared classes. |
| `_shared/landing.css` | Copy of the real landing stylesheet. |
| `_shared/bootstrap.min.css` | Bootstrap 5.3. |
| `_shared/leaflet.css` | Leaflet (maps are images in these mockups). |
| `_shared/mock.css` | Mockup-only chrome. Not shipped. |
| `_shared/photo-placeholder.svg` | Neutral stand-in for accident photos. |

If a shared component (button, badge, card, table, modal) needs to change, make
the change once in `_system/index.html` + `_system/system.css` and tell the
integrator. Do not create five different button styles in five screens.

## Rules

- Keep **Bootstrap 5** and the existing CSS tokens: `--kerb`, `--asphalt-2`,
  `--asphalt-3`, `--guide`, `--lane`, `--acc`, `--siren`, `--line`, `--ink`,
  `--muted`.
- **No Tailwind, no new CSS frameworks, no new fonts, no build step.**
- Do not rename existing semantic classes. Prefix new classes with
  `rr-<screen>-` so they cannot collide.
- Keep the page responsive at **1440, 1024, 768 and 390 px**.
- Keep keyboard focus visible (`:focus-visible` is already styled).
- Respect `prefers-reduced-motion`.
- No real personal data. Accident photos are already replaced with a placeholder;
  keep it that way. Do not add real names, emails, phone numbers or plate numbers.
- **Do not add JavaScript.** Scripts are stripped when the mockup is converted
  back. Keep interactions as static states or CSS.
- Do not edit other screens. One screen per handoff.

## Annotations (important)

The mockups carry a few attributes so the returned HTML can be turned back into
JSX without guessing.

### Region markers

```html
<section data-rr-region="filter-bar" data-rr-source="src/pages/Reports.jsx">
```

Keep these. They tell the integrator which part of the real page a block came
from. `data-rr-repeat="rows"` marks a repeated row group, and
`data-rr-component="..."` marks a component boundary.

For converter-driven repeats use the annotation form `data-repeat` described
below. `data-rr-repeat` on its own is only a region marker and stays on the
markup as documentation.

### Dynamic expressions

Use `{{ ... }}` for anything that comes from data. It works in text and
attributes:

```html
<td class="code-cell">{{ r.report_code }}</td>
<span data-component="StatusBadge" data-status="{{ r.status }}"></span>
<span data-if="loading" class="page-loading">Loading…</span>

<tr data-repeat="r in reports" data-key="r.id">
  ...
</tr>
```

- `{{ expression }}` → `{expression}`
- `data-component="StatusBadge" data-status="{{ r.status }}"` → `<StatusBadge status={r.status} />`
- `data-if="expr"` → `{expr && ( ... )}`
- `data-repeat="r in rows"` + `data-key="r.id"` → `{rows.map((r) => ( ... ))}`

If you do not use these, the converter still produces a static JSX file and the
integrator wires the data by hand. The annotations just make it faster and less
error-prone.

### Static media

Charts and maps are `<img>` tags with `data-rr-static="chart"` or
`data-rr-static="map"`. Leave them as images. Keep their frames and dimensions;
replace the frame styling if you like, but do not try to make the image
interactive.

## What to return

Return the whole screen folder, or at minimum:

1. `index.html`
2. `screen.css`
3. `notes.md`

`notes.md` must list:

- what changed visually
- any **structural** change (new panel, moved field, removed control)
- new class names
- states you covered (default, empty, loading, error, mobile)
- anything the integrator must re-wire

If you change the shell or a shared component, say so explicitly. Those are
global changes.

## For the integrator

```bash
# regenerate all mockups from the running app
npm run mock:export

# one screen
npm run mock:export -- --screen reports

# convert a returned mockup into a reviewable JSX file
npm run mock:convert -- \
  --in html-mockups/_screens/reports/index.html \
  --out src/pages/Reports.mock.jsx \
  --component ReportsView \
  --router

# compare the mockup with the running page
npm run mock:verify -- --screen reports
```

The converter never overwrites a real page. It writes a `.mock.jsx` file, plus a
`.report.md` listing anything it could not convert. Integration is a review step:
re-attach state, handlers and service calls, run the existing `check:*` scripts,
and compare screenshots.

Notes:

- `--router` turns `data-rr-href` links into `<Link to="...">`; omit it to keep
  `<a href="...">`.
- `--check` parses and reports without writing anything, and exits non-zero when
  there are warnings. Use it in review/CI.
- `--force` is needed to replace an existing file. Without it, both `.mock.jsx`
  and any non-mock output are protected.
- Chart/map screenshots and the photo placeholder are rewritten to
  `/html-mockups/...` URLs so the JSX can be pasted into the app for review. The
  report reminds you to replace them before shipping.
